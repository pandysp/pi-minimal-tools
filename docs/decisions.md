# Decisions (pi-minimal-tools v1)

Why v1 looks and behaves the way it does, including where it deliberately differs from Claude Code. The reference captures and working notes lived in a session scratch folder and are not kept.

Decided by the agent after the user said "when in doubt KISS, decide yourself" (2026-09-26). Earlier decisions made by the user are listed first for completeness.

## Made by the user

| # | Decision |
|---|---|
| U1 | Build our own extension (option B), not a fork |
| U2 | Failed look-around commands are shown in full (Claude Code hides them) |
| U3 | No merging of neighbouring look-around calls in v1 |
| U4 | No "files changed by this command" rows in v1 |
| U5 | Overwriting a file looks like writing a new file (no before/after diff) |
| U6 | No seconds counter while a command runs |
| U7 | Wording-only changes to other tools are out. Stock read/write/edit rows stay |
| U8 | Claude Code's dots: green = succeeded, red = failed, white = agent reply, on bash, write and edit rows |
| U9 | Blinking dot is out of scope: the running dot is steady grey |
| U10 | Must work with @gotgenes/pi-anthropic-auth and pi-hydra; verify with the full setup loaded |

## Made by the agent

| # | Decision | Why | Alternative |
|---|---|---|---|
| A1 | Row style: pi's own `$ cmd` with the dot in front, not Claude Code's `Bash(cmd)` / `⎿` | Consistent with write/edit rows, which keep pi's drawing | Claude Code's framing |
| A2 | Register the tools in `session_start` with `ctx.cwd`, and restore the active tool set right after | Stock pi builds its tools and the extension context from the same session folder (`agent-session.js:155, 175, 2612`), and a second registration by the same extension replaces the first (`loader.js:225`). So new, resumed and forked sessions get the right folder. Verified by reading pi's code, not by a live /new + resume run | A live tmux check with /new and resume |
| A3 | Test the row states (finished, running, failed, expanded) through pi's real row component (`ToolExecutionComponent`) in vitest; tmux replay only for "nothing else changes" and the test C line count | Deterministic, fast, and exercises pi's own drawing path | Replays for everything |
| A4 | Look-around = a **single** command: `ls` (list), `cat` `head` `tail` `wc` (read), `grep` `rg` `find` (search). Pipes, `;`, `&&`, `\|\|`, any redirect (even `2>/dev/null`), `$(…)`, backticks, `&`, multi-line, env prefixes, and `find -delete/-exec…`, `rg --pre` are "work" | Strict allow-list: a wrong "look" could hide a change or a failure, a wrong "work" only shows a few lines too many. Updated after the silent-failures review (A17) | A broader list (tree, fd, sort, git status…) |
| A5 | A summary line always says "1" ("Listed 1 directory") | No merging in v1, and only single commands collapse, so each call is one thing | Counting files/patterns per call |
| A6 | Named cases from the sorting table: `git status` / `git diff` = work (matches Claude Code's full rows); `grep … 2>/dev/null` = work (any redirect); `cd src && ls` = work (`cd` not on the list); `awk`, `sed` = work (both can write files); `cat a \| sort \| uniq` = work (sort/uniq dropped from the list) | Same strict rule as A4; the first is observed Claude Code behaviour, the rest are ours | Allow-listing any of them |
| A7 | While a bash command runs: grey dot + command; `Running…` until the first output, then stock pi's live tail of the latest lines | Claude Code and stock pi both show the latest output while a command streams; reusing stock's drawing is the simplest faithful option | Plain `Running…` until done |
| A8 | Ctrl+O shows stock pi's expanded bash row unchanged, without a dot | No wrapper code; add the dot later only if its absence looks wrong | Dot on the expanded row too |
| A9 | Collapsed output drops empty lines before taking the first 3 and counting `… +N lines` | Blank lines waste the 3-line budget (e.g. `(no output)` + blank + `Command exited with code 1`) | Keep blank lines |
| A10 | Dot colours are Claude Code's exact 256-colour codes (green 114, red 211, grey 246, white 231), not pi theme colours | Matches the reference exactly; the dot is the only fixed colour we add | Map to pi theme colours (success/error/muted) |
| A11 | A single `grep`/`rg` with exit code 1 and no output → finished search (summary line), not a red row. Checked in a real run: pi marks it as an error (`isError: true`). Exit code 2 (real error), pipes, lists and multi-line scripts stay red | Otherwise every search without results would look like a failure | A general exit-code rule per command |
| A12 | Write/edit dot colour comes straight from the call context: `isPartial` → grey, `isError` → red, else green. No shared state | pi keeps `isPartial` true until the final result (`tool-execution.js:24, 131`) and redraws the call row on every update (`:245`). (Corrected: an earlier version of this row wrongly said the context can't tell running from done.) | State set by the result renderer |
| A13 | Write/edit keep the dot in the expanded view too; bash's expanded view has none (A8) | Write/edit are "stock + dot" in every state, so no extra branch; bash hands Ctrl+O to stock unchanged | Same rule for both |
| A14 | pi silently swallows errors in a tool's drawing code and shows just the tool name. Our drawing code is wrapped in `loud()`, which shows a red `pi-minimal-tools: drawing failed: …` line instead. Stock renderers always get `lastComponent: undefined`, because handing them our component was the crash that revealed this | Fail loudly (handbook); a pi update that breaks a row becomes visible | Rely on tests only |
| A15 | Reply dot `⏺` carries no colour of its own: it takes the terminal's default text colour, like the reply text (measured: only `\x1b[49m` before it). Not verified to be Claude Code's exact white (231); that depends on the terminal's colour scheme | pi's markdown transformer only feeds markdown; colour codes in markdown are not safe to rely on | Exact 231 via a message renderer (more code, touches pi's message drawing) |
| A16 | Reply dot logic adapted from pi-cc-style-tools (MIT, newCman1): assistant text only, never before a code block, never doubled | Reuse over reinvention; credited in the code | Write our own rules |
| A17 | **Moved target, please review.** Only single commands collapse; `ls -la /usr/bin \| head -80` and `ls; true` now get full rows, although Claude Code collapses them | Independent silent-failures review (Codex) reproduced `cat /missing \| head` and `cat /missing; true` showing only "Read 1 file": the exit code belongs to the last command, so an earlier failure hid. This breaks rule U2 (failures always visible). Cost: test C grows from about 7 to about 11 lines (Claude Code 6, stock pi 21); the planned "≤ 8 lines" target becomes "≤ 11" | Keep Claude Code's pipe collapsing and accept hidden failures |
| A18 | Broken settings files: no extra error handling of our own | Measured: stock pi prints `Warning: Invalid settings file …` and continues with defaults; our settings object reads the same files and lands on the same defaults. Throwing would diverge from stock (tools would not register). Tested: with the extension, pi still warns and sends the identical request | Drain `SettingsManager` errors and throw |
| A19 | The red crash line names the tool (`pi-minimal-tools: drawing the bash row failed: …`), nothing more | Review suggested stack/phase details; kept minimal | Stack, cause and phase in the message |
| A20 | The "nothing else changes" check runs on everything before and after the tool calls in a replayed session, not line by line inside the tool region | Detecting tool-row boundaries from screen colours proved unreliable (tmux only writes colour changes; fullscreen pads with blank lines). The read row is untouched by construction, since read is not taken over | Colour-based row detection |
| A21 | Test C measured on the same replay, same method as the reference count: stock pi 18 lines, ours 11, Claude Code 6 (yesterday's stock count of 21 used a different capture) | Same method for both sides in one run | Compare against yesterday's 21 |
| A22 | Final verification installs the extension project-locally (`pi install -l`) in a scratch folder, not into `~/.pi/agent/settings.json` | The plan was to leave the user's settings alone until they ask to install; a project install loads the user's full setup plus ours, exactly like a real install | Install globally for the check |
| A23 | Collapsed running bash rows never show stock's `Elapsed N s` line; the expanded view (Ctrl+O) keeps it, as stock | Stock only shows it once its own call row has started a timer, so it appeared only after the first Ctrl+O: inconsistent. Leaving it out matches the user's "no seconds counter" (U6). Found by the streaming Ctrl+O test | Always show it (stock's collapsed behaviour) |
| A24 | While the model is still typing a command, the row shows `$ ...` like stock pi (not `$ undefined`); `Running…` stays until the first real output line | Both found in the live run's frames; `$ ...` checked against stock's row in the same state (an earlier version wrongly claimed stock shows a bare `$`) | — |
| A25 | **No reply dot** when a reply starts with a heading, list, quote, table or code block; the dot goes only before plain text | A dot in front breaks markdown (`# Heading` became `⏺ # Heading`, code blocks lost their fence). Found by the code review | Put the dot after pi has rendered the markdown (more code, touches pi's message drawing) |
| A26 | Any `$` or `{…}` in a command makes it "work"; quotes and backslashes are removed before checking dangerous options (`"-delete"`, `-de\lete`, `--pre=x`) | The shell expands and decodes these, so `find . $X` or `find . {-delete,}` could delete files while showing "Searched for 1 pattern". Found by the code review (the `$`/`{}` cases were added by the agent) | Treat any quote as "work" (would turn every `grep 'x'` into a full row) |
| A27 | When a bash command finishes, stock's own result drawing always runs once (its output discarded in the collapsed view) | Stock stops the timer its expanded view may have started; skipping it left pi redrawing forever. Found by the code review | Clear stock's timer field ourselves |
| A28 | Write/edit rows are drawn 2 columns narrower, then the dot goes in front; each bash preview line is cut to one screen line | Otherwise the dot cut off file names in narrow windows, and one long output line took many screen lines. Found by the code review | Truncate after adding the dot / let long lines wrap |
| A29 | **Chained commands stay full rows (user, 2026-09-26).** In a real session the model sent chains like `cd … && git status && ls -R \| head -50 && cat …`, so no summary line appeared at all | Decided after the real-use spin. Options considered: ignore a leading `cd <dir> &&`; collapse `&&`-chains of look-around commands (safe, since `&&` stops at the first failure); also count `git status/log/diff` as look-around | Any of those three |
| A30 | **Bash and write rows are drawn without pi's frame** (`renderShell: "self"`). One blank line between rows instead of about four; the dot moves to the left edge with output indented by 2 (Claude Code's layout, matching the reply dot). Ctrl+O shows stock's expanded drawing without the frame. Edit already draws its own frame in stock pi and keeps its extra blank line | The user found the gaps between rows too large (screenshots 2026-09-26). Measured in a replay: 41 → 18 blank lines in the tool region | Keep the frame; trim blank lines ourselves |
| A31 | Tests switch off any installed copy of this package via project settings (`"extensions": []`) and resume fixture sessions in the test folder; every run checks which bash pi used | After the global install, the "stock" runs silently loaded the extension too, so comparisons were ours-vs-ours | Uninstall around tests |
| A32 | Renamed from `pi-claude-tools` to **`pi-minimal-tools`** (user, 2026-09-26) | The old name described the inspiration, not the function, sounded Claude-only, and was easy to confuse with `pi-claude-code-ui` / `pi-claude-style-tools`. Several similar extensions already use quiet/calm/zen/tidy | `pi-minimal-ui`, `pi-foldaway` |
| A33 | **Long commands are cut like in Claude Code (user, 2026-09-27):** a collapsed row shows at most the first 2 lines and 160 characters of the command, then `…` right after the last visible character (a blank 2nd line is dropped, as in Claude Code); wrapped lines hang under the `$`. Ctrl+O shows the whole command | Before, the header printed the whole command, so a heredoc script filled the history. Measured in Claude Code 2.1.283 in tmux: a script showed 2 lines + `…`; a one-line command was cut at exactly 160 characters at both 60 and 120 columns, so the limit counts characters, not screen lines | Cap by screen lines |
